# 業務プロセスと課題ページ生成スキル

ライトアップ『AI業務変革白書』の「【◯◯】業務プロセスと課題」ページと**全く同じデザイン・構成**で、
任意の業界・職種のプロセス資料（PDF）を作る。出力は 1280×720px（16:9）の横スライドPDF。

## ワークフロー（必ずこの順番で）

このスキルの肝は **「いきなり作らない」** こと。工程の分解は業界知識が要るうえ、順番を間違えると
資料の信頼性が崩れる。だから必ず次の2段階で進める。

### ステップ1: 工程分解案を提示して承認を得る

ユーザーが業界・職種（例「コールセンター」「歯科クリニック」「SaaS営業」）を伝えてきたら、
まず `references/approved/` に類似業界の承認済みJSONがないか確認し、あれば1件Readして叩き台にする。
その上で業務プロセスを自分の知識で分解し、**テキストで** 次の要素を提示してユーザーの確認を得る。
（この時点ではまだPDFを作らない）

提示する内容:
- **レイアウト種別**: フェーズ列型（`phases`）か、対象者レーン型（`lanes`）か。
  - `phases` … 時系列のフェーズ（例：受付→対応→記録→分析）で区切る。大半の業界はこちら。
  - `lanes` … 対象者で分ける（例：対求職者／対企業）。人材・仲介など「相手が複数いる」業務向け。
- **工程（ステップ）**: ①②③…の通し番号付きで、正しい前後関係の順に列挙。各フェーズ/レーンに割り振る。
- **特に負荷の高い工程（3〜4個）**: どの番号が重いか。ここが赤ハイライト＆課題カードになる。
  赤ハイライトには必ず根拠を添える——(a) 工数の目安（例: 1件あたり◯分×月◯件）、(b) 公的統計・
  業界調査の出典、(c) ユーザーからのヒアリング、のいずれか。根拠を示せない工程は赤にせず、
  承認時にユーザーへ確認する。
- **各課題の一言説明**: 負荷工程ごとに「誰が・どの工程で・何に時間を取られるか」を具体化して1〜2文で。
- 業界統計を使う場合は出典（機関名・年）が必須。示せなければ使わない
  （`skills/_shared/writeup-facts.md` の引用ルールに従う）。

提示したら「この工程分解と順番で問題ないですか？修正があれば教えてください」と確認する。
**順番の妥当性は特に念入りに確認すること**（後工程が前に来ていないか等）。

### ステップ2: 承認後、本資料と同じデザインでPDF生成

承認が取れたら、合意した内容を JSON にして `scripts/render.py` で HTML を生成し、
ヘッドレス Chrome/Edge で PDF 化する（後述）。生成後は必ず目視確認し、レイアウト崩れ・
はみ出し・改行の乱れ・順番をチェックしてから渡す。
完成後、承認済みJSONを `references/approved/` に保存するかユーザーに確認する。

## 生成手順（Windows 前提）

この環境には soffice / libreoffice / pdftoppm / weasyprint は無い。HTML→PDF は
**ヘッドレス Chrome/Edge** で行う（両ブラウザとも導入済み）。フォントは Windows 標準で代替する。

1. **データJSONを書く**（形式は `scripts/render.py` の冒頭ドックと下の例を参照）。一時ファイルは
   スクラッチパッドに置く。
2. **HTML を生成**（`render.py` は HTML を必ず書き出す。PDF 化はしない）:
   ```powershell
   python scripts\render.py input.json 業務プロセスと課題.pdf --html-only
   ```
   これで `業務プロセスと課題.pdf.html` が出力される（`--html-only` を付けなくても、
   weasyprint が無い当環境では自動で HTML のみになる）。
3. **HTML→PDF はヘッドレス Chrome/Edge で行う**。参照実装 `monthly-report-deck\scripts\html-to-pdf.ps1`
   を流用する（Chrome→Edge を自動探索し、`--print-to-pdf`／フォント読込待ち込みで16:9 PDF化）:
   ```powershell
   powershell -ExecutionPolicy Bypass -File ..\monthly-report-deck\scripts\html-to-pdf.ps1 `
     -Html "業務プロセスと課題.pdf.html" -Pdf "G:\マイドライブ\outbox\YYYYMM\業務プロセスと課題.pdf"
   ```
4. **目視確認**: 生成した HTML を Read（またはブラウザ）で確認し、レイアウト崩れ・はみ出し・
   改行の乱れ・順番をチェックしてから PDF 化する。
5. 完成物は `G:\マイドライブ\outbox\YYYYMM\`（当月フォルダ）に保存する。ホームディレクトリ
   直下への直置きは禁止。computer:// リンクは使わない。パスをそのまま伝える。

> フォント注記: 本エンジンは `IPAexGothic,"Noto Sans JP",sans-serif` を指定するが、Windows 環境に
> Noto 系が無ければヘッドレス Chrome/Edge は Windows 標準の日本語フォント（Meiryo / Yu Gothic 等）で
> 代替レンダリングする。豆腐（□）にはならない。

## データ形式（要点）

キー構成のみ抜粋（完全な入力例は **`references/example_input.json` 参照**）:

```json
{
  "pages": [{
    "cat": "AI業務変革白書 ／ コールセンター",   // 右肩の小見出し
    "title": "インバウンド",                      // 【title】業務プロセスと課題
    "leads": ["…リード文1", "特に<b>「一次応答」…</b>の業務負荷が高い"],
    "layout": "phases",                          // "phases"（列型）or "lanes"（レーン型）
    "hot": ["④", "⑥", "⑧"],                     // 負荷の高いステップ番号＝赤ハイライト＝課題と対応
    "groups": [ ["受付", [["①","着信受付"], ["②","本人確認"]]], … ],
    "challenges": [ {"t":"④ 一次応答", "b":"…なぜ大変か", "icon":"headset"}, … ],  // 3〜4枚
    "pageno": "04"
  }]
}
```

`pages` に複数入れれば複数業務（例：インバウンド／アウトバウンド）を1つのPDFに連続生成できる。
`icon` に使えるキー一覧は `scripts/render.py` 冒頭ドックを参照。

## デザイン・構成の留意点（本資料の作成過程で確定したルール。必ず守る）

これらは実際の制作で繰り返し調整した結果なので、外すと「白書と同じ」にならない。

- **順番を崩さない**。工程は番号順に並べ、フェーズ/レーン内は左→右・上→下へ矢印（›／⌄）でつなぐ。
  前後関係が読み手に一目で伝わることが最重要。承認時に必ず順番を点検する。
- **不自然な改行を作らない**。ステップ名はチップ幅に収め、収まらないときだけ「・」「（」「/」など
  自然な位置で折り返す（`process_engine.wrap_label` が処理）。語の途中で切れる機械的分割は避ける。
  どうしても長い語が多い場合は `phases`（列型）にするとチップが広くなり収まりやすい。
- **余白は詰める**。間延びさせない。フロー図と課題カードでページ下まで自然に埋める。
- **フッターは消さない**。各ページ下部に「株式会社ライトアップ／著作権表記／ページ番号」を必ず残す。
- **ロゴは右上に控えめに**。`assets/writeup_logo.png`（writeup! の実ロゴ）を使う。自分で文字ロゴを作らない。
- **配色は白背景＋ブランド赤 `#B8202E` ＋紺 `#15233F`**。ビジネス資料らしく上品に。
  （この `#B8202E` は白書再現のため意図的。社内標準赤は `#C8102E` だが、本スキルでは白書に合わせて `#B8202E` を使う。混同しないこと）
- **負荷の高い工程は赤でハイライト**し、その工程を下部の**課題カード**（3〜4枚・ラインアイコン付き）に対応させる。
  `hot` に入れた番号のチップが赤くなる。課題カードの見出し番号と一致させること。
- **アイコンはラインアイコン**（細い線・ブランド色）。`icon` キーで指定（一覧は render.py 冒頭）。
- 文章・数字は勝手に脚色しない。ユーザーが承認した内容をそのまま使う。

## 技術メモ（レンダリングの落とし穴。ここを外すと生成に失敗する）

- **PDF化はヘッドレス Chrome/Edge**（`monthly-report-deck\scripts\html-to-pdf.ps1` 流用）。当 Windows
  環境には soffice / libreoffice / pdftoppm / weasyprint が無いので使えない。`render.py` は HTML を
  生成するところまでを担い、PDF 化はブラウザに委ねる。`setup_env.sh` は Linux サンドボックス用の
  レガシー（当環境では不要）。
- **日本語フォントは Windows 標準で代替**する。エンジンは `IPAexGothic,"Noto Sans JP",sans-serif` を
  指定するが、Noto 系が無ければヘッドレス Chrome/Edge が Meiryo / Yu Gothic 等で描画する。豆腐（□）
  にはならない。`~/.fonts`＋`fc-cache` の手順は Linux 用で、Windows では不要。
- **`--virtual-time-budget` でフォント読込を待つ**。`html-to-pdf.ps1` が処理する（既定5000ms）。
  文字が反映されないときはこの値を上げる。
- **ネストした flexbox は避ける**（旧 weasyprint 由来の制約の名残）。CSSテーブルか inline SVG を使う。
  **プロセス図は必ず SVG**で描く（`process_engine.process_svg`）。HTMLテーブルでプロセス図を組むと
  特定の行が崩れる事象があったため、SVG固定にしている。
- レンダリング（HTML生成）は104ページでも数秒。1〜数ページなら一瞬。バックグラウンド実行は不要。

## 近いスキルとの使い分け（発動精度）

- **提案書・提案資料の全体**（AIインパクトの1次提案デッキ等）を作るなら **ai-impact-proposal-deck**。
  本スキルは「業務プロセスと課題」ページ（プロセス分解＋課題整理の白書1ページ）単体の生成に特化する。
  提案書の中の1ページとして本ページが欲しいだけなら本スキルを使い、提案書全体は ai-impact 側に寄せる。

## ファイル構成

```
business-process-deck/
├── SKILL.md
├── scripts/
│   ├── process_engine.py   # アイコン／折返し／プロセスSVG／CSS／ページHTML生成
│   ├── render.py           # JSON → HTML（CLI）。PDF化はヘッドレスChrome/Edgeに委譲
│   └── setup_env.sh        # 【レガシー】Linuxサンドボックス用（weasyprint＋IPAexGothic）。Windowsでは未使用
├── assets/
│   └── writeup_logo.png    # writeup! ロゴ（右上用・透過PNG）
└── references/
    ├── example_input.json  # 入力JSONのサンプル
    └── approved/            # ユーザー承認済みの業界別工程分解JSONライブラリ（README.md参照）
```
